# Source Trace Manifest

This manifest records the source routines that the next emitted binary should
port first. It is the working contract for source-guided emission: read the C,
then write Python emitter routines that generate equivalent x86 machine code.

## Important Source Ordering

`P_SetupLevel` loads these map structures in this order:

```text
P_LoadBlockMap
P_LoadVertexes
P_LoadSectors
P_LoadSideDefs
P_LoadLineDefs
P_LoadSubsectors
P_LoadNodes
P_LoadSegs
P_GroupLines
P_LoadReject
P_LoadThings
```

The first source-guided stage intentionally stops after `P_LoadLineDefs`. That
keeps the slice small while preserving the real dependency order: linedefs need
loaded vertexes, sidedefs, and sectors.

## Notes From Initial Read

- `W_CheckNumForName` scans backwards when no lump hash table exists. The first
  emitted stage can use that linear path before implementing `W_GenerateHashTable`.
- `W_LumpLength` and `W_ReadLump` are good early ports because their behavior is
  small but they exercise the real lump directory layout.
- `P_LoadVertexes` is the cleanest first map conversion routine: each 4-byte map
  vertex becomes two 32-bit fixed-point coordinates.
- `P_LoadLineDefs` should come after sectors and sidedefs because it stores
  front/back sector pointers derived through sidedef indexes.

## source_stage01 Implementation Notes

- The emitted path is generated by `tools/emit_source_stage01_wad_map.py`.
- The executable reads the full WAD directory into `lump_directory` at runtime;
  `wad_check_num_for_name` uses the same backwards linear scan Chocolate Doom
  uses before its lump hash table exists.
- Map lump selection follows the `ML_*` offsets from `doomdata.h`, matching
  the `P_SetupLevel` order for `MAP01`.
- The first slice keeps texture and flat names as raw 8-byte names because the
  texture/flat managers are later source-guided slices.

## source_stage02 Implementation Notes

- The emitted path is generated by `tools/emit_source_stage02_bsp_setup.py`.
- The output filename contains `setup`, so the PE writer embeds a minimal
  `asInvoker` manifest resource to avoid Windows installer-elevation
  heuristics while preserving the required executable name.
- `P_GroupLines` intentionally stops before blockmap-derived sector block boxes
  because blockmap loading is outside this slice. The releasable proof is the
  source-ordered subsector sector assignment and sector line grouping.
- The pinned `third_party\freedoom\freedoom2.wad` `MAP01` smoke signal is:
  `V=1189 L=1274 SD=2041 SEC=211 SS=698 N=697 SG=2233 ROOT=696 G=3..81 F0=16`.

## source_stage03 Implementation Notes

- The emitted path is generated by `tools/emit_source_stage03_bsp_walk_debug.py`.
- The executable reuses the stage02 WAD/map/BSP setup and seeds `viewx`,
  `viewy`, and `viewangle` from the pinned `MAP01` player-one start
  `(-192, -192, 0)`.
- `render_point_on_side` ports the source vertical/horizontal fast paths,
  sign-bit shortcut, and fixed multiply comparison used by Doom BSP ordering.
- `render_bsp_node_debug` follows source recursion order. The back child is
  always traversed through `render_check_bbox_accept_all`, documenting the
  stage03 boundary before real `R_CheckBBox` visibility in stage04.
- `render_debug_subsector` is intentionally a counter/debug adaptation: it
  records visited seg indexes for a top-down framebuffer highlight and leaves
  planes, sprites, `solidsegs`, and wall columns untouched.
- The pinned `third_party\freedoom\freedoom2.wad` `MAP01` smoke signal is:
  `V=1189 SEC=211 SD=2041 L=1274 SS=698 N=697 SG=2233 VN=697 VSS=698 VSEG=2233 DEPTH=33 FIRSTSS=227 LASTSS=169`.
